# 案例：车辆与停车位信息系统

在飞书妙搭（Spark）上为一家香港公用事业集团的运输团队构建的内部车队管理应用。本文描述生产系统；本仓库的公开 demo 用同一套前端代码跑在合成车队上，身份类字段遮蔽。

## 1. 背景

团队用一份 Excel「Fleet List」主表加宏驱动的 Logbook 维护车队档案，另在飞书多维表格里放了一份副本。任何车辆变更（归属部门、运输协调人、停车地点、状态）都靠邮件或聊天提出，由管理员先录入多维表格草稿表，之后再手工誊到 Excel 主表，宏才能生成 Logbook 行。查一辆车停在哪里，要打开 Base 找到那一行，再打开关联的停车场记录和平面图附件。

## 2. 做了什么

四个页面，一份共享的变更类型注册表：

- **查询** — 按车牌（输入一个字符即出候选，十二个车辆字段白名单，结果卡显示停车场名称与平面图，平面图可放大）或按停车场（限高、汽车升降机、可停车种、充电设备等属性，平面图与街景，停在该场的车辆表可按车牌和部门筛选，点一行跳回车牌模式）。管理员额外看到可折叠的「Full Details」，把 Fleet List 其余列按 登记 / 财务 / 设备 / 其他 分组。
- **新建申请** — 购物车模式。选车、选变更类型，表单随之变化：字段类变更显示 Log-From（从车辆记录实时读当前值）和 Log-To（候选值取自该列去重值、停车场列表或手动输入）；补领卡类和「其他」改为必填描述。草稿存在服务端，可编辑、删除，一次整批提交。
- **审批**（管理员）— 双栏控制台：左侧待审批列表，右侧详情含编辑历史徽标、附件预览、Edit / Reject / Approve。顶部状态条显示已批准、已到生效日但尚未写回的条数，抽屉里对比当前值与新值并执行写回。
- **After Approval**（管理员）— 「Fleet Record Updates」：已批准且日期已到的 Logbook 行，全选、按 Excel 宏要求的六列顺序复制 TSV、标记完成。下方「Follow-up」：需要线下处理的已批准申请（补领卡、其他），勾选标记完成。隐藏的历史图标打开 **申请档案**：所有非草稿申请，按车牌 / 类型 / 状态 / 日期筛选，分页，展开看详情与编辑历史。
- **我的申请** — 申请人自己的提交，含状态、审批意见和编辑历史。管理员可用「View as regular user」切换到这个视角。

## 3. 架构

```
React 19 + TypeScript 客户端 ── capabilityClient ──▶ 多维表格插件实例（Fleet List DRAFT、Parking Location & Map）
        │
        └── axiosForBackend /api ──▶ NestJS（妙搭全栈）──▶ PostgreSQL（Drizzle）：change_requests、logbook、administrators
                                          │
                                          ├──▶ 多维表格写插件（batchUpdateRecords）+ 读回校验
                                          └──▶ 平台文件存储（附件）
```

见 `docs/architecture.mmd` 与 `docs/data-model.mmd`。

客户端通过平台 capability 直接读车辆表和停车场表做搜索和联想；所有改状态的操作走 API。API 是三个 NestJS 模块：`change-requests`（草稿生命周期）、`approval`（管理员的一切操作）、`parking-locations`（反向检索），共用 `shared/api.interface.ts` 一份 TypeScript 契约和 `shared/change-types.ts` 一份注册表。

## 4. 数据模型

`change_requests` 一行装下整个申请生命周期：类型、车辆（多维表格 record id 加车牌作为稳定业务主键）、Log-From / Log-To、生效日期、备注、附件（JSONB）、状态、审批人、审批时间与意见、`vehicle_synced_at`、`edit_history`（JSONB）、`follow_up_completed_at`。`logbook` 行在批准时生成，自带 `sync_status` 供 Excel 导出。`administrators` 是一列平台用户 id。

车辆档案本身留在多维表格。应用不复制它，只读需要的列，每条批准的变更只写回一个字段。

## 5. 关键决策

**一份注册表，两个布尔。** 每个变更类型是 `shared/change-types.ts` 里的一行，带 `writesLogbook`（这条变更最终要不要回 Excel 主表）和 `syncsVehicleField`（批准时是否写回车辆记录）。字段类变更是 true/true；「Remark on change」是 true/false；补领卡与「其他」是 false/false。模块加载时断言不变式：写车辆记录的类型必须同时写 Logbook（否则 Excel 和 Base 静默分叉）、必须声明列名、带未实现副作用处理器的类型不能启用。此前这些信息散落在前后端五处。

**写回按生效日期分流。** 批准一定记录决定和 Logbook 行，但只有生效日期是今天或更早才写车辆记录。未来生效的等着；状态条统计已批准、已到期、未写回的条数，管理员在抽屉里看着当前值与新值执行写回。

**写、读回、重解析。** 多维表格的写入不被信任，直到读回记录且字段等于期望值。写入或校验失败时，服务按车牌重新解析 record id（Base 曾整体重新导入过一次，所有 record id 都会重生成）并重试一次。失败即抛错；批准是事务，写回失败让申请留在待审批，而不是「批准成功但什么都没发生」。

**宁可报错，不要静默。** 项目曾两次被静默无操作咬过（插件字段映射为空、同步状态标志读错）。未登记的类型、未实现的处理器、缺失的列都抛出带修复提示的错误。

**测试模式。** 一个环境变量把批准和写回限制在白名单测试车牌上，用于灰度；客户端显示琥珀色横幅，并在导出表里标出测试行，避免被复制进主表。

**英文显示，中文存储。** 状态值、多维表格选项值、变更类型 id 是与 Base 和 Excel 宏共享的中文契约值。界面是英文，唯一的映射出口是 `client/src/data/labels.ts`，存储值从不翻译。

**管理员可编辑并留痕。** 管理员可以在批准前修正待审批申请（类型、值、日期、备注）；每次编辑追加一条 `{ editedAt, editedBy, changes[] }`，申请人看到「Edited」徽标和差异。

## 6. 值得记住的事故

- 多维表格里的停车场关联列名与映射函数读的名字不一致，提取器返回空串，停车位置区块永远显示「未关联」。三处调用点各自命名该列，现在共用一个。
- 沙箱里登录守卫放过匿名调用，空 user id 进入 `user_profile` 比较，PostgreSQL 返回 `42846`。管理员校验现在在任何查询之前拒绝空 id。
- 平台拒绝 AI 发起的插件实例修改；字段映射只能在插件面板手改，并对着投影 schema 确认，因为读侧缺字段和空值无法区分。

## 8. 公开 demo 改了什么
